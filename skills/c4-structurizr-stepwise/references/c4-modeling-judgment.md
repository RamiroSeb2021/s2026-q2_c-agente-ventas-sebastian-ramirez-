# C4 Modeling Judgment

Use C4 to communicate static software structure through hierarchical zoom. It is not a design process, completeness checklist, folder map, endpoint inventory, or proof that the architecture is good.

## Core Principles

- Model the story the audience needs to understand now.
- Keep each view at one abstraction level.
- Prefer fewer boxes with clear responsibilities over complete inventories.
- A box should represent something real, intended, or deliberately proposed. Ask: would we code it that way, or did we code it that way?
- Use names that stakeholders recognize. Avoid implementation slang unless the audience is technical and the term exists in code or deployment.
- Capture assumptions, unresolved questions, and invented notation in the legend or notes.
- Review a level before continuing; errors compound as the model zooms in.

## Level Boundaries

### C1 System Context

Show the target software system in its environment: people, external systems, and high-level purpose relationships. This view is for technical and non-technical stakeholders to agree on scope and responsibilities.

Omit containers, databases, components, queues, protocols, endpoints, classes, functions, deployment topology, and internal technology choices.

### C2 Container

Open the target system boundary into major runnable units and data stores: web apps, mobile apps, APIs, workers, schedulers, queues, databases, and external-facing integration adapters when they are independently meaningful.

Show responsibilities, key technology choices, and inter-container communication. Preserve C1 actors and external systems when they explain who uses the containers or what the system integrates with.

Omit internal components, packages, controllers, functions, endpoint lists, and low-level framework objects.

### C3 Component

Decompose one container at a time into coarse-grained components with distinct responsibilities. Components should reflect the architecture style and map to real or intended code modules, services, adapters, repositories, controllers, or domain capabilities.

Skip C3 for data stores, tiny CRUD services, or simple microservices unless the decomposition teaches something useful. Avoid modeling generic logging, config, middleware, auth plumbing, and other cross-cutting concerns unless they are architecturally central.

### C4 Code

C4/code is optional and usually not recommended. Use it only for the internals of one complex component, a critical algorithm, or a pattern template where class/code relationships explain a design decision.

Omit autogenerated class dumps, ORM entity catalogs, DTO inventories, and framework boilerplate.

## Relationships

- Label every relationship with purpose: `Submits report`, `Reads indexed chunks`, `Publishes notification`.
- Avoid repeated vague labels such as `uses`, `calls`, or `depends on`.
- Add mechanism/style only when useful: `HTTPS/JSON`, `Async message`, `SQL`, `MCP stdio`.
- Keep direction meaningful from actor/source of action to target/capability.
- Remove lines that do not help the diagram's story.

## Audience Guidance

- C1: mixed technical/non-technical stakeholders; confirm scope and external dependencies.
- C2: developers, operations, support, security, and technical stakeholders; confirm deployable/runtime shape and data ownership.
- C3: developers maintaining one container; confirm internal responsibility boundaries.
- C4: implementers of one component; confirm a narrow code-level pattern.

## What Not To Draw

- Everything that exists just because it exists.
- Folder structures or package trees with no architectural meaning.
- Every endpoint, command, class, helper, DTO, migration, or test fixture.
- Future technology that is not a target decision or clearly labeled proposal.
- Containers/components that do not have a responsibility distinct from their neighbors.

## Anti-Patterns

- Mixing C1 actors, C2 containers, C3 components, and C4 classes in one view.
- Jumping from a black-box system directly to all components and calling it C2.
- Treating a diagram as complete because Structurizr syntax validates.
- Drawing fantasy architecture that ignores the repo reality for a technical audience.
- Creating component boxes that nobody would implement, name, deploy, or maintain.
- Using generic names like `Manager`, `Service`, `Helper`, or `Processor` without a domain responsibility.
